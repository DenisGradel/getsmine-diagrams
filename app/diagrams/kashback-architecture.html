Как теперь проходит изменение.

Разработка больше не смешивает дизайн-проверку, Git, production и резервные копии. У каждого шага есть свой владелец и понятная проверка результата.

Денис работает локально, stage показывает эту версию.

Код темы Kashback и плагина Kashback Core передаётся на stage как файлы. База, медиа, секреты и WordPress core не гоняются туда-сюда автоматически.

Для дизайн-проверки достаточно одной человеческой фразы: “Stage сейчас показывает последнюю локальную версию, можно проверять дизайн.”
Stage закрыт паролем, не индексируется и не отправляет реальные внешние действия.
Если stage отстал, сначала сверяются файлы, а не обсуждается дизайн по старой версии.

Путь кода, данных и медиа.

Самое важное: код, база и медиа больше не едут одним опасным комом. У каждого направления своя логика.

КодMac → stage для проверки → Git → Deployer → closed production.
БазаПереносится только отдельной принятой операцией; daily backup маленький DB-only.
МедиаНе синхронизируются постоянно; попадают в full backup и restore drill.
СекретыЖивут в owner-маршрутах, в страницу и Git не попадают.
StageПоказывает текущие локальные файлы для дизайна, но не становится production.
ProductionЗакрыт, проверен, но публичный домен ещё не направлен на него.
ОткатЕсть кодовый откат и backup/recovery путь.

Что значит “future launch package”?

Это свежий полный Duplicator-пакет в `production/prelaunch/`, который нужен перед будущим переключением публичного домена. Он не переключает домен сам.

Что Денису делать с дизайном дальше?

Ориентироваться на stage. Перед проверкой агент должен сказать одной понятной фразой: “Stage сейчас показывает последнюю локальную версию, можно проверять дизайн.”
